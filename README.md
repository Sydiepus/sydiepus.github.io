# sydiepus.github.io

Pixel-art personal site with a markdown blog. No framework and no bundler —
the homepage and blog are generated by Python from JSON and markdown.

Palette, sprite and favicon all come from one 32×32 pixel-art potato.

---

## Setup

Needs [uv](https://docs.astral.sh/uv/). Nothing else — no Node, no global
Python packages.

```bash
uv sync          # creates .venv/ and installs markdown, pygments, pyyaml
```

`uv run` auto-syncs, so after cloning you can skip straight to building.

---

## Writing a post

```bash
uv run build.py --new "Reading a binary config format"
```

Scaffolds `src/posts/reading-a-binary-config-format.md` with front matter and
`draft: true`. Write it, flip the draft flag, then:

```bash
uv run build.py            # build into build/
uv run build.py --serve    # build + preview at http://localhost:8899
```

Output lands in `build/blog/<slug>.html`, and `build/blog.html` is regenerated
as the index. **`build/` is wiped on every build**, so renaming or deleting a `.md`
never leaves an orphaned page behind — the generated tree always matches
`src/posts/`.

### Front matter

Only `title` is required.

```yaml
---
title: Reading a binary config format
date: 2026-08-20          # defaults to the file's mtime
summary: Shown on the blog index. Auto-extracted if omitted.
tags: [python, reverse engineering]
draft: false              # true = skipped by the build
slug: custom-url          # defaults to the filename
---
```

Supported markdown: tables, fenced code with syntax highlighting, footnotes,
blockquotes, nested lists, `attr_list`. Smart quotes and dashes are on.
Reading time is estimated automatically and shown in the post header.

A post with no front matter still builds — it warns and derives the title
from the filename.

## Deploying to GitHub Pages

Repo must be named `<username>.github.io` and pushed to `main`:

```bash
git init
git add .
git commit -m "pixel site + blog"
git branch -M main
git remote add origin https://github.com/Sydiepus/Sydiepus.github.io.git
git push -u origin main
```

Or let the `gh` CLI create the repo and push in one step:

```bash
gh auth login                      # once
gh repo create Sydiepus.github.io --public --source=. --push
```

The repository includes `.github/workflows/pages.yml`. It builds `build/` and
deploys that directory automatically on every push to `main`. In repository
settings, choose **Settings → Pages → Source: GitHub Actions**.

Live at `https://sydiepus.github.io` after the workflow completes.

## Layout

```
src/
  assets/           source CSS, JavaScript, images, and photos
  data/             homepage and photography content
  posts/            markdown blog posts
build/              GENERATED deployment directory — do not edit
src/
  index.py          homepage renderer
  blog.py           blog page renderer
  page.py           shared HTML shell
  photos.py         photography page renderer
tools/              audits and maintenance scripts
build.py            build entry point
pyproject.toml      deps, pinned in uv.lock
```

Projects are stored in the `projects` array in `src/data/site.json` and rendered
into `build/index.html` by `uv run build.py`. Homepage copy, navigation,
metadata, upstream entries, about text, statistics, contact details, and footer
text live in `src/data/site.json`. Each project entry requires
`name`, `description`, `tags`, and `status`; add `url` for public projects
and omit it for private projects. An optional `code` field renders an inline
installation command. The build validates the array, escapes content for
HTML, rejects duplicate names, and checks project URLs before updating the
homepage.

Blog title, description, labels, empty-state text, and reading-time wording
also live in the `blog` object in `src/data/site.json`.

The photography page is rendered by `src/photos.py` from `src/data/photos.json`.
Each photo entry requires `image`, `camera`, and `film`; optional `title`,
`place`, `alt`, and `app` values add descriptive text or app information.
Images and `.mp4` videos are supported. Run `uv run build.py` after changing
the JSON.

To remove embedded metadata from all JPGs in `src/assets/photos`, run:

```bash
uv run --with pillow python tools/clear_photo_metadata.py
```

The script preserves filenames and image/audio streams while removing JPG
metadata and MP4 container metadata.

`src/assets/site.css` and `src/assets/site.js` are copied into the generated
site and shared by the homepage
**and** every generated one, so the blog can't visually drift from the site.
Blog-specific styles live at the bottom of `src/assets/site.css` under the `BLOG`
banner.

Two things that will bite if you forget them:

- `site.js` runs on pages that have no ticker, stat card or theme button, so
  every element lookup in it must stay null-guarded.
- The theme is applied by a small **blocking** script in each `<head>`.
  `site.js` is deferred; without that snippet, night-theme visitors get a
  flash of rose before it corrects.

## Editing the site itself

Edit `src/index.py` for homepage layout changes and `src/data/site.json` for content
changes, then run the build. The renderer escapes JSON-derived content before
inserting it into the HTML document.

### Pixel rules

Keep these or the 8-bit illusion breaks:

- `border-radius` is `0` everywhere
- text shadows are hard pixel offsets, never blurred
- animations use `steps()` so motion snaps instead of glides
- spacing is a multiple of `--px` (4px)
- code uses real monospace, **not** Press Start 2P — the pixel font has no
  useful glyph metrics at code sizes

### Colour rules

All four palette colours are sampled from the GitHub avatar.
`src/assets/logo.png` **is** that avatar, byte-for-byte, and the sprite has
exactly four colours:

| hex | role |
|---|---|
| `#d95763` | rose — `--rose` / `--brand` |
| `#d9a066` | tan — `--tan`, night accent |
| `#8f563b` | bark |
| `#663931` | cocoa |

```bash
uv run --with pillow python tools/rose_check.py    # re-sample + audit the rose
python tools/contrast_verify.py                   # exit 0 = both themes pass AA
python tools/panel_lint.py                        # exit 0 = no page tokens on panels
```

`contrast_verify.py` parses the real `var()` chains out of `src/assets/site.css` and
also asserts `--rose` still equals the avatar's `#d95763`, so a drifted
brand colour fails the check rather than going unnoticed. `panel_lint.py`
is described under *Two polarities* below.

**The light theme is keyed to the potato, not to the backdrop.** This is
the single most important thing to know before touching it.

The avatar is 81.5% rose, but that rose is the *field behind* the sprite.
The subject — the potato — is tan, bark and cocoa, all sitting at hue
10–30° (warm brown). Rose sits at 354° (red-pink). Earlier versions built
the page surface on the rose hue, and the result read pink and soft. The
current surface is built on the tan hue instead: warm parchment, brown
text, rose demoted to a sparing accent. Same sprite, keyed to what it
actually depicts.

### Token naming

`--sand-*` are the light theme's own values. The unprefixed
`--bg` / `--fg` / `--panel` / `--accent` are the **active** values, and
they are what a rule should reference — `[data-theme="night"]` overrides
only the unprefixed names. Never reference `--sand-*` outside the token
block.

| token | sand | role |
|---|---|---|
| `--bg` | `#f8f1ea` | parchment page |
| `--fg` | `#33200f` | deep bark-brown text, 13.85:1 |
| `--panel` | `#fffdf9` | card surface, a touch lighter than the page |
| `--panel-fg` | `#33200f` | text on a card, 14.68:1 |
| `--panel-accent` | `#b72937` | accent on a card, 6.10:1 |
| `--panel-line` | `#33200f` | hairlines drawn *inside* a card |
| `--panel-shadow` | `#33200f` | the cast shadow — this is what lifts a card |
| `--brand` | `#d95763` | exact avatar rose, large/non-text, page only |
| `--accent` | `#b72937` | darkened rose, small text, page only |
| `--muted` | `#8f563b` | recedes without going grey |

### Panel elevation — read this before changing `--panel`

**Lift comes from the cast shadow, not from the fill.** A hard offset
shadow only reads as depth when it contrasts with the card it falls from,
which means the card has to be *lighter* than its own shadow.

This was got wrong once, instructively. Panels were set to cocoa
`#663931` — a genuinely dark card, **8.55:1** from the page, which sounds
like strong elevation and measured like it. It read as a flat brown blob,
because:

```
border --fg  vs the card   1.62:1     edge invisible
shadow --ink vs the card   1.72:1     shadow invisible
```

Card, border and shadow were three dark browns merging into one shape.
Separation from the *page* is not the same property as lift, and no
single-number check catches the difference.

So `contrast_verify.py` now measures **both** mechanisms and requires one
of them to be doing real work:

- (a) **fill separation** — panel leaves the page's lightness band (≥3:1)
- (b) **cast shadow** — panel sits near the page, shadow lifts it (≥3:1
  against the *fill*)

The sand theme uses (b): fill is 1.10:1 from the page, shadow is
**15.26:1** from the fill. The night theme uses (a). Both pass.

Throw distances are `2·--px` at rest, `3·--px` for `.pbox-raise`, and
`4·--px` on linked `.work:hover` cards (where the card also rises one unit,
so hover reads as picking it further off the page).

### Two surfaces

Page and panels are both light in the sand theme, so `--panel-*` currently
resolve close to the page tokens. **Keep using them in panel rules
anyway.** Night gives panels different values, a dark panel has already
been tried here once, and a rule that reaches for `--fg`/`--accent` inside
a card is a latent bug even while it happens to render fine.

`panel_lint.py` enforces this. It is not a pure-CSS check: `.links` is
written as a bare selector but renders inside `.card`, so nothing in the
stylesheet marks it as panel context. The linter parses the **HTML** to
learn which classes actually render inside a panel, then flags CSS rules
targeting them with page-only tokens. It caught exactly that bug in
`.links a::before` (1.54:1 on the old cocoa panel) — a CSS-only version of
the same check missed it.

Two earlier attempts were rejected, both for reasons the audit can't see:

- **Rose as the page surface.** It *passes* AA — rose is a mid-tone, so
  while light text on it caps at 3.82:1, dark text reaches 5.49:1, and the
  whole theme measured clean. It was reverted because a fully saturated
  mid-tone red across an entire page is tiring to read against. High
  chroma over large areas is a comfort problem; no contrast ratio reports
  it. Don't re-derive it from the numbers.
- **Paper/pink surface** (`#fff3ee` with `#f7ddd2` panels). Passed
  everything, but pastel pink at high lightness reads girly, and because
  the panels were pink-tinted too it was the whole surface, not one accent.

**Two accents, split by WCAG text size.** The exact avatar rose is 3.42:1
on parchment: that clears the 3:1 bar for large text (≥24px) and non-text
UI, and fails the 4.5:1 bar for small text. Nearly every accent usage here
is small — Press Start 2P at `--t-micro`/`--t-label` computes to 8–9px —
so small text uses the darkened `--accent`. If the rose looks wrong
somewhere, check which token the element uses before changing a hex value.

Four more traps the audits exist to catch:

- **Don't hardcode `rgba(0,0,0,...)` washes.** Code chips and the XP bar
  track did; a black wash only works under light text on a dark panel. Use
  `--chip-bg` (page) / `--chip-panel-bg` (panel) / `--track-bg`.
- **Opacity is not a free dial.** Below about `.68`, even `--fg` on `--bg`
  drops under 4.5:1. Use `--dim-page` on the page and `--dim-soft` inside
  a panel; they differ because the surfaces have different headroom.
- **Keep interactive surfaces consistent.** Linked `.work:hover` cards use
  the same colors as buttons through panel-scoped aliases
  (`--panel-accent` and `--panel-accent-contrast`).
  Private project rows remain on their panel surface and do not lift.
- **`--ink` is not a usable shadow on a light theme.** It's near-black, as
  is `--fg`, so the hard title shadow vanishes. Display headings use
  `--title-shadow`; the accent word, which is itself `--brand`, uses
  `--brand-shadow` or it casts no shadow at all.

The CRT scanline overlay is per-theme (`--scan-opacity`). It was authored
for a dark page; at full strength on a light surface it reads as grey
banding across body copy rather than phosphor glow. It also tints every
screenshot — sampled pixels come back darker than the token value, which
is the overlay, not a wrong colour.

**Screenshotting:** pass `--force-prefers-reduced-motion` to headless
Chromium. Without it the `.reveal` transition is captured mid-fade and
panels sample as a washed-out blend (measured `#a88f88` instead of
`#663931`), which looks exactly like a colour bug and isn't one.

### Nav overflow

The pixel font is wide. A fourth visible nav link overflows at 390px
(`scrollWidth` jumps 390 → 468), which is why secondary links carry
`hide-sm`. Re-check mobile width after touching the nav.

## Privacy

Deliberately pseudonymous: handle only — no legal name, employer,
university or city, and no LinkedIn link (that profile carries the real
name).

Two things to keep in mind:

- The GitHub account itself lists a real name, so this reduces exposure but
  does not anonymise.
- A static host serves **every** file in the directory. Old drafts and CV
  files are not private just because nothing links to them. `.gitignore`
  blocks `*.typ`, `*.pdf` and `*.docx` for that reason — keep CV-style copy
  outside the repo.

## Troubleshooting

| Symptom | Cause |
|---|---|
| Post missing from index | `draft: true` still set |
| `duplicate slug` error | two posts resolve to the same filename; set `slug:` |
| Blog looks unstyled | `build/assets/site.css` not found — run the build |
| Flash of wrong theme | the blocking `<head>` theme snippet was removed |
| Bullets missing in a post | site reset reapplied; `.article-body ul` needs `list-style` |
